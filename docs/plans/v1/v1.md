# V1 Implementation Plan

## 1. Purpose

This document is the living V1 roadmap for Appointment Assistant.

It translates the stable product and architecture documentation into an ordered backlog of implementation milestones and vertical slices.

This document is intentionally **not** a complete technical design of the V1.

Future slices are defined only deeply enough to preserve ordering, dependencies and expected outcomes. Detailed implementation decisions are made when a slice becomes active, using the code that actually exists at that moment.

Roadmap location:

- `docs/plans/v1/v1.md`

Sources of truth:

- `docs/product.md` — product behavior, functional requirements and Business rules;
- `docs/architecture.md` — system structure and architectural boundaries;
- `docs/adr/` — accepted architectural decisions and their rationale;
- `docs/reference-business.md` — canonical reference scenario and seed/demo data used to exercise the generic product.

If this plan conflicts with those documents, the stable source of truth takes precedence and the plan must be updated.

`docs/reference-business.md` is a canonical fixture and acceptance scenario, not a source of Business-specific domain design. It may reveal missing generic capabilities, but implementation must not introduce Lúmina-specific concepts or rules into the core product.

---

## 2. Working model

V1 is developed through small vertical slices and short feedback loops.

The default cycle for an active slice is:

1. understand the slice goal and acceptance criteria;
2. inspect the current implementation;
3. read the relevant product, architecture and ADR context;
4. perform an impact check against the rest of the known V1;
5. resolve only the technical decisions required for the active slice;
6. add or update tests for the relevant behavior;
7. implement the smallest coherent solution;
8. run the relevant automated checks;
9. review the resulting code and integration impact;
10. refactor when the implementation reveals a real abstraction or structural problem;
11. leave the slice ready for Developer review and commit.

The backlog is deliberately mutable.

A future slice may be split, merged, reordered, added or removed when implementation evidence justifies it. Changes to the backlog must not silently change product scope or accepted architectural decisions.

The implementation must not speculate about future functionality merely to make later slices easier.

---

## 3. Planning depth

### Stable now

The following are defined before development begins:

- V1 milestones;
- vertical slices;
- major dependencies;
- high-level slice outcomes;
- milestone exit criteria.

### Defined when a slice becomes active

The following are normally deferred until the slice is active:

- exact classes and modules;
- migrations and schema details;
- endpoints and request shapes;
- jobs and event structures;
- DTOs;
- provider-specific implementation details;
- detailed test cases;
- refactoring steps;
- exact file changes.

This keeps technical decisions grounded in the current codebase rather than in assumptions made weeks earlier.

### Requirement traceability

Each implementation slice includes a `Covers` field.

`Covers` identifies the Product functional requirements (`FR-xx`) and Business
rules (`BR-xx`) that the slice materially addresses. It is traceability metadata,
not a claim that the slice completes every listed requirement by itself.

A requirement may therefore appear in multiple slices when its behavior crosses
application, conversational or integration boundaries.

Cross-cutting operational slices may state that they cover V1 operational
readiness without introducing a standalone Product requirement.

### Active slice plans

Detailed implementation is not maintained in this V1 roadmap.

When a slice becomes Active, its implementation is planned in a dedicated file
under:

`docs/plans/v1/slices/`

The active slice plan contains only the implementation detail required for that
slice, based on:

- its goal and acceptance direction in this document;
- the Product requirements identified by its `Covers` field;
- the relevant architectural constraints;
- relevant ADRs;
- the implementation that actually exists at that moment.

A slice plan may be divided into small implementation tasks when this improves
reviewability, learning or validation.

Future slice plans are not created in advance.

The intended planning structure is:

```text
docs/
└── plans/
    └── v1/
        ├── v1.md
        └── slices/
            ├── S01-business-information.md
            ├── S02-services-professionals.md
            └── ...
```

This keeps V1 implementation artifacts grouped together and leaves a clear path
for future versions such as `docs/plans/v2/`.

---

## 4. Status model

Slices use one of the following states:

- `Pending` — known future work;
- `Ready` — dependencies are satisfied and the slice can be detailed;
- `Active` — currently being designed or implemented;
- `Blocked` — cannot proceed because a dependency or external action is unresolved;
- `Done` — acceptance criteria and validation are complete.

Only one implementation slice should normally be `Active` at a time.

---

## 5. Definition of Ready

A slice is ready to enter implementation when:

- its goal is clear;
- its user or Business value is understood;
- its important dependencies are satisfied;
- its relevant acceptance criteria can be stated;
- the current codebase has been inspected;
- relevant product, architecture and ADR constraints are understood;
- required manual prerequisites are either completed or explicitly identified.

Being Ready does **not** require designing every internal implementation detail.

---

## 6. Definition of Done

A slice is Done when:

- its agreed acceptance criteria are satisfied;
- relevant automated tests have been added or updated;
- the existing relevant test suite remains green;
- applicable static, linting, type and build checks pass;
- external services are replaced by fakes or test doubles in normal automated tests where appropriate;
- the implementation remains consistent with `product.md`, `architecture.md` and accepted ADRs;
- no known regression introduced by the slice remains unresolved;
- documentation is updated only where the implementation changes an established source of truth;
- any manual or external verification required by the slice has been completed or explicitly recorded as not verified;
- the resulting change is small enough to review meaningfully before commit.

A slice is not Done merely because code has been generated or because its happy path works manually.

---

## 7. System coherence checkpoints

Vertical slices must remain coherent with the complete system.

Before implementing a slice, perform an impact check:

- What existing domain concepts does this slice reuse?
- What invariants must remain true?
- Does the proposed implementation conflict with a known later V1 requirement?
- Is the design introducing a new architectural decision?
- Can an existing abstraction support the slice without distortion?
- Is a refactor justified by current evidence rather than speculation?

At the end of each milestone, perform an integration checkpoint:

- run the complete available automated suite;
- verify the milestone against the relevant product requirements;
- review the current implementation against architecture boundaries;
- identify accumulated duplication or structural friction;
- perform justified refactors before building the next milestone;
- review whether upcoming slice ordering still makes sense.

If an active slice requires changing an accepted architectural decision, implementation pauses until the decision is discussed and, when appropriate, documented through an ADR.

# Milestone 0 — Foundation

**Status:** Done  
**Owner:** Developer

## Goal

Establish a minimal, understandable and continuously validated project foundation before feature development begins.

The Developer implements this milestone directly in order to become familiar with the main technologies, project structure and development workflow before delegating feature implementation.

## Scope

Foundation includes only infrastructure required to develop V1 safely.

It must establish:

- Laravel backend bootstrap;
- React + TypeScript + Vite frontend bootstrap;
- PostgreSQL development and test persistence;
- Redis availability for the application;
- local environment configuration;
- backend automated testing foundation using PHPUnit;
- frontend automated validation foundation;
- CI through GitHub Actions from the beginning of development;
- reproducible dependency installation and builds;
- initial project structure consistent with `docs/architecture.md`;
- a minimal path for loading reference Business configuration required by early slices.

Exact versions and setup choices are decided while executing this milestone and recorded by executable project configuration rather than duplicated here.

## Explicitly not required yet

- production deployment;
- CD;
- real WhatsApp connectivity;
- real Google Calendar connectivity;
- real OpenAI calls;
- complete Business seed data beyond what early slices require;
- speculative infrastructure for later slices.

## Exit criteria

- backend can run locally;
- frontend can run locally;
- PostgreSQL is usable by the backend and by automated tests;
- Redis connectivity required by the application foundation is available;
- backend tests can run successfully;
- frontend validation/build can run successfully;
- GitHub Actions executes the agreed CI checks;
- a clean checkout can be prepared using documented project configuration;
- no product feature implementation is required to consider Foundation complete.

# Milestone 1 — Core read capabilities

## Goal

Implement deterministic Business capabilities before introducing conversational AI or external messaging channels.

These slices expose executable Laravel application capabilities that later interfaces will reuse.

## S01 — Business information

**Status:** Done
**Depends on:** Milestone 0
**Covers:** FR-01

### Goal

Provide configured customer-facing Business information through the application.

### Outcome

The application can retrieve the information required by `FR-01` without using the LLM or embedding Business values in conversational prompts.

### Acceptance direction

The active-slice plan must cover at least:

- configured Business information can be retrieved;
- unavailable information is not invented;
- reference Business data can exercise the capability;
- relevant behavior is protected by automated tests.

## S02 — Services and Professionals

**Status:** Done  
**Depends on:** S01
**Covers:** FR-02; BR-01; BR-02

### Goal

Expose the Service catalogue, prices, durations, Professionals and Professional-Service eligibility.

### Outcome

The application can answer the deterministic data needs behind `FR-02` and the eligibility requirements used by scheduling.

### Acceptance direction

The active-slice plan must cover at least:

- active Services can be retrieved;
- Service descriptions can be retrieved when configured;
- Service price and duration are authoritative configuration data;
- eligible Professionals can be determined from configuration;
- invalid or inactive Service references fail safely.

## S03 — Appointment availability

**Status:** Done  
**Depends on:** S02
**Covers:** FR-03; BR-01; BR-02; BR-03; BR-04; BR-05; BR-13

### Goal

Calculate valid Appointment slots from authoritative Business and scheduling state.

### Outcome

The application can satisfy `FR-03` without the conversational layer calculating availability itself.

### Acceptance direction

The active-slice plan must cover at least:

- Service duration and scheduling buffers;
- Professional-Service eligibility;
- Business operating schedule;
- Professional recurring availability;
- breaks and unavailable periods;
- temporary exceptions and blocks;
- existing active Appointment occupancy, proved independently of authoritative Appointment persistence; the persisted source is connected in S05;
- explicit Professional preference;
- an explicitly requested Professional is never silently substituted;
- when no Professional is requested, valid availability preserves the
  Professional choices so that the Customer can choose without automatic assignment;
- valid alternatives when appropriate;
- no automatic Professional prioritization.

Availability rules require strong automated test coverage because later Appointment operations depend on them.

# Milestone 2 — Customer and Appointment lifecycle

## Goal

Implement the authoritative transactional core for Customer identity and Appointment management.

Appointment-changing operations must remain deterministic and testable independently from AI and external integrations.

## S04 — Customer registration and identity

**Status:** Done  
**Depends on:** Milestone 1
**Covers:** FR-14; BR-07

### Goal

Create and resolve persistent Customers required to own real Business Appointments.

### Outcome

The application supports the registration and identity behavior defined by `FR-14` and `BR-07`.

### Acceptance direction

The active-slice plan must cover at least:

- registration is required before creating a real Business Appointment;
- first name and at least one surname are required and persisted;
- supported channel identity is associated with the Customer;
- an existing channel identity resolves the same Customer;
- phone is optional contact data and may be persisted when provided;
- refusal to provide a phone number does not prevent registration or booking;
- Customer identity persists independently from Conversations and Appointments.

S04 implements the provider-independent registration and identity rules. The real WhatsApp identity flow is connected and verified end-to-end when the WhatsApp integration becomes active.

## S05 — Create Appointment

**Status:** Active  
**Depends on:** S03, S04
**Covers:** FR-04; FR-11; BR-04; BR-05; BR-06; BR-07; BR-10; BR-13; BR-14

### Goal

Create a confirmed Appointment for a registered Customer using current authoritative scheduling state.

### Outcome

The application implements `FR-04` and the relevant creation rules.

### Acceptance direction

The active-slice plan must cover at least:

- registered Customer ownership;
- valid Service;
- selected eligible Professional;
- final availability revalidation;
- concurrency protection;
- no overlapping active Appointments;
- confirmed Appointment persistence;
- authoritative persisted active Appointments provide occupancy data to the availability calculation established in S03;
- a shared append-only Appointment audit mechanism is established;
- audit records preserve the action, timestamp, actor or system component, action source and relevant before/after state;
- creation produces the corresponding audit record;
- clear failure when a previously available slot is no longer valid.

## S06 — View Appointments

**Status:** Pending  
**Depends on:** S05
**Covers:** FR-05; BR-06; BR-07

### Goal

Allow an identified Customer to retrieve only their own relevant Appointments.

### Outcome

The application implements `FR-05` and enforces Appointment ownership.

### Acceptance direction

The active-slice plan must cover at least:

- Customer-specific Appointment retrieval;
- multiple Appointment handling;
- Appointment identification;
- returned Appointment information includes Service, Professional, date/time and status;
- no cross-Customer information exposure.

## S07 — Reschedule Appointment

**Status:** Pending  
**Depends on:** S05, S06
**Covers:** FR-06; FR-11; BR-04; BR-05; BR-06; BR-07; BR-08; BR-10; BR-13; BR-14

### Goal

Move an existing Appointment to another valid slot while preserving consistency.

### Outcome

The application implements `FR-06` and `BR-08`.

### Acceptance direction

The active-slice plan must cover at least:

- ownership;
- applicable rescheduling policy;
- replacement-slot validation;
- current state revalidation;
- original Appointment remains valid until success;
- Professional reassignment when explicitly selected and valid;
- rescheduling produces the corresponding audit record through the shared audit mechanism;
- Professional reassignment is represented in the corresponding audit record;
- concurrency safety;
- unchanged original Appointment on failure.

## S08 — Cancel Appointment

**Status:** Pending  
**Depends on:** S05, S06
**Covers:** FR-07; FR-11; BR-06; BR-07; BR-09; BR-10; BR-14

### Goal

Cancel a Customer Appointment according to configured Business policy.

### Outcome

The application implements `FR-07`, `BR-09` and Appointment lifecycle rules.

### Acceptance direction

The active-slice plan must cover at least:

- ownership;
- configurable cancellation restrictions;
- reference Business minimum-notice rule;
- transition to cancelled state;
- cancelled Appointment releases availability;
- Appointment record is preserved;
- audit history is preserved and extended.

## S09 — Complete Appointment lifecycle

**Status:** Pending  
**Depends on:** S05
**Covers:** BR-06; BR-14

### Goal

Complete the Appointment lifecycle required by the product.

### Outcome

The application supports the `completed` lifecycle state required by `BR-06` without relying on the conversational assistant to infer or apply state changes.

### Acceptance direction

The active-slice plan must cover at least:

- confirmed Appointments can transition to completed through an application-owned mechanism;
- only valid lifecycle transitions are allowed;
- completion produces the corresponding audit record through the shared audit mechanism;
- completed Appointments remain part of Business history;
- completed Appointments do not occupy scheduling availability;
- completed Appointments cannot be rescheduled or cancelled through normal Customer operations.

The exact completion mechanism is defined when this slice becomes Active based on the implementation and operational workflow that exist at that time.

### Outcome

### Acceptance direction

The active-slice plan must cover at least:

- Conversation persistence;
- active conversational state;
- conversation history stored separately from active state;
- continuity across relevant turns;
- replacement of explicitly changed information;

- Customer and Appointment data remain independent from Conversation lifetime.

**Status:** Pending  
**Depends on:** S01, S02, S03, S10
**Covers:** FR-01; FR-02; FR-03; FR-08

### Acceptance direction

The active-slice plan must cover at least:

  colloquial or incomplete expressions, context-dependent references, relative
  dates and times and alternative ways of referring to Services or actions;

  again unnecessarily;
- application tools/capabilities for Business information;
- Service and Professional information;
- availability;
- no direct persistence access by the LLM;

## S12 — AI Appointment operations

**Status:** Pending  
**Depends on:** S04, S05, S06, S07, S08, S10, S11
**Covers:** FR-04; FR-05; FR-06; FR-07; FR-08; FR-14; BR-07; BR-10; BR-13

### Goal

Allow natural-language conversations to drive Customer registration and Appointment-changing capabilities safely.

### Outcome

The conversational assistant can invoke the authoritative application operations for:

- Customer registration;
- Appointment creation;
- viewing Appointments;
- rescheduling;
- cancellation.

### Acceptance direction

The active-slice plan must cover at least:

- required confirmation/clarification behavior;
- successful registration can continue the active Appointment flow without
  restarting the Conversation or requesting already established information;
- ownership remains application-enforced;
- AI cannot bypass Business rules;
- AI cannot infer successful writes;
- Appointment-changing success is communicated only after the authoritative
  application operation reports successful persistence;
- conversational context does not replace persistent Customer or Appointment state;
- tool results determine the response to Appointment-changing actions.

## Goal

## S15 — Customer reminders

**Status:** Pending  
**Depends on:** S05, S07, S08, S13
**Covers:** FR-12; BR-11

### Goal

Schedule and deliver Customer Appointment reminders according to Business configuration.

### Outcome

The application implements `FR-12` and `BR-11`.

## S16 — Google Calendar synchronization

**Status:** Pending  
**Depends on:** S05, S07, S08, S13
**Covers:** FR-09; BR-10; BR-12

### Goal

Reflect authoritative Appointment state in the Business operational Google Calendar.

### Outcome

### Manual prerequisites

This slice is expected to contain actions marked `[Developer]`, including Google account/project configuration, Calendar configuration, credentials and permissions.

Exact manual actions are defined when the slice becomes Active.

### Acceptance direction

The active-slice plan must cover at least:

- Appointment creation creates the corresponding schedule representation;
- rescheduling updates it;
- cancellation updates or cancels it appropriately;
- Professional reassignment is eventually reflected in the operational schedule;
- schedule representations contain the Customer, Service, Professional, start time, end time and relevant Appointment status;
- Professional schedules remain distinguishable;
- synchronization is idempotent enough to avoid duplicate representations;
- synchronization failure does not invalidate Appointment state;
- failed synchronization can be retried or reconciled.
